Os arquivos do backend que devem ser enviados para análise são principalmente JwtAuthenticationFilter.java, JwtService.java e SecurityConfig.java. Durante a implementação houve um problema importante com JWT. O Auth Proxy estava gerando um Google ID Token, que usa assinatura RS256. O backend possuía um JwtService antigo que esperava JWT próprio assinado com HS256 usando jwt.secret. Isso causou o erro UnsupportedJwtException: The parsed JWT indicates it was signed with the 'RS256' signature algorithm, but the provided SecretKeySpec key may not be used to verify RS256 signatures. Isso aconteceu porque o token IAM do Google estava chegando ao backend e sendo processado pelo JwtAuthenticationFilter como se fosse o JWT da aplicação. Esse problema foi identificado como sendo uma questão de arquitetura: existem dois tipos de autenticação diferentes. O Google ID Token serve para autenticar a comunicação frontend Cloud Run → backend Cloud Run. O JWT da aplicação serve para autenticar o usuário depois que ele faz login. O backend não deve tentar validar o Google ID Token usando o JwtService da aplicação. Foi necessário alterar a lógica do backend para que o token IAM do Google não seja tratado como o JWT do usuário. O código atual do JwtAuthenticationFilter.java, JwtService.java e SecurityConfig.java deve ser analisado pela outra IA antes de novas alterações, porque mudanças anteriores nesses arquivos foram feitas durante a tentativa de resolver o conflito entre IAM e JWT. Outro problema ocorrido foi com o Auth Proxy em Go. Inicialmente ele usava o metadata server diretamente para obter o ID Token. Depois foi alterado para usar a biblioteca google.golang.org/api/idtoken. Isso criou problemas de dependências. Em determinado momento o go.mod passou a depender de google.golang.org/api em uma versão que exigia Go 1.24, enquanto o Dockerfile usava golang:1.23-alpine. O build falhou com a mensagem de que google.golang.org/api@v0.249.0 exigia Go >= 1.24. Depois houve outro erro porque o Dockerfile tentou copiar proxy/go.sum, mas esse arquivo não existia localmente. O erro foi "/proxy/go.sum": not found. Depois, quando o go.sum foi removido do COPY, o build chegou até a compilação, mas falhou com missing go.sum entry for module providing package google.golang.org/api/idtoken. Portanto, o estado atual do código Go/dependências precisa ser revisado. A outra IA deve escolher uma solução simples e estável para o Auth Proxy, evitando criar uma cadeia desnecessária de dependências. Também houve um erro inicial no Go porque os estava importado e não era utilizado. Esse erro já foi identificado. Outro problema ocorreu no Cloud Run porque o primeiro frontend não estava ouvindo corretamente na porta esperada. O Auth Proxy passou a ouvir a porta 8080 e o Nginx continuou servindo o frontend. Nos logs do Cloud Run apareceu Auth proxy iniciado na porta 8080 e Default STARTUP TCP probe succeeded ... on port 8080, então a revisão chegou a ficar saudável. Em uma revisão anterior, o frontend retornou Whitelabel Error Page 500. Os logs mostraram que o container iniciou corretamente, com Nginx e Auth Proxy, mas houve erro de aplicação. Depois uma versão posterior voltou a funcionar e o login foi realizado com sucesso. A versão de imagem que estava sendo utilizada para o frontend seguro foi identificada como secure-v4. O repositório completo da imagem é southamerica-east1-docker.pkg.dev/project-bb29153a-91af-47dd-8df/zadinventory/frontend:secure-v4. O serviço Cloud Run do frontend é frontend e o serviço do backend é backend. O domínio do frontend é https://frontend-571647583940.southamerica-east1.run.app. O domínio do backend é https://backend-571647583940.southamerica-east1.run.app. O Artifact Registry é zadinventory. O objetivo final é manter o backend protegido por IAM, sem permitir acesso público direto, e permitir que o frontend Angular continue usando normalmente URLs como /api/auth/login, /api/usuarios etc., sem precisar colocar credenciais IAM no navegador. É importante não remover a proteção IAM do backend apenas para fazer o frontend funcionar. O teste que confirmou a proteção foi justamente o acesso direto ao backend retornar 404 Page not found, enquanto o mesmo endpoint pelo domínio do frontend retornou 200 OK. Há também um problema de segurança no endpoint /api/usuarios: o teste mostrou que ele retorna a senha BCrypt do usuário na resposta JSON. Isso é uma vulnerabilidade independente do IAM e deve ser corrigido no backend, fazendo com que a entidade/DTO retornada pela API nunca exponha o campo senha.
